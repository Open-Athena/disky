## Infrastructure boundary

Own Pages project `oa-r2-usage`, hosts `r2.oa.dev` and `dev.r2.oa.dev`, D1 `oa-r2-usage-db`, KV `oa-r2-usage-cache`, and private derived bucket `oa-r2-usage-index`. These do not adopt or mutate the CW/GCS resources. Local passphrase-encrypted state lives at `infra/cf/state/`; its new private `.envrc` holds the passphrase. Back up both; do not treat them as temporary benchmark data or publish credentials.

The deployment also owns independent GCP state (`infra/gcp/state/`), scheduler, scan/builder/scheduler service accounts, secret containers, image repository, archive bucket `oa-r2-usage-data` and scratch bucket `oa-r2-usage-scratch`. It shares project `oa-internal-450019`, Cloudflare account and zone with the other OA deployments. The two existing CW/GCS index buckets are included only as read-only inventory sources, alongside the Marin buckets; the site serves solely from its own derived bucket and D1. Changing or destroying this stack does not manage the CW/GCS stacks or resources. The D1 token's account-wide API permission is documented below; deployment resources being independent does not create a separate cloud-account security boundary.

The publisher token can read/write only the new derived bucket. `index-reader` is read-only on that bucket and is the credential the site gets. `source-reader` is read-only on exactly `marin-na`, `marin-discord`, `oa-cw-s3-usage-index` and `oa-gcs-usage-index`; it is for the remote scanner, never the site. R2's read permission includes both listing and reading objects; the scan only lists metadata. Changing a token's ignored policy requires an explicit replacement/rotation, not an assumed in-place update. Existing CW/GCS tokens are unchanged.
